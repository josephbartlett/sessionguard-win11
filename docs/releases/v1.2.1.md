# SessionGuard 1.2.1

Patch release focused on tightening restart-signal interpretation so noisy registry rename entries do not look like a confirmed Windows reboot by themselves.

## Highlights

- downgraded `PendingFileRenameOperations` so it no longer counts as a definitive pending reboot signal on its own
- updated the dashboard card label from `Windows restart` to `Restart status`
- removed the duplicate `Open dashboard` tray-menu entry
- added regression tests for ambiguous protected-session restart states

## Included in this release

- updated `RegistryRestartSignalProvider` so pending file rename operations are treated as low-confidence restart evidence
- kept the broader restart model intact for higher-confidence CBS and Windows Update reboot signals
- updated the main dashboard card label to better match ambiguous restart evidence
- updated tray primary-action behavior so the contextual slot is only used for real actions instead of repeating the fixed dashboard command
- added tests in:
  - `tests/SessionGuard.Tests/RestartStatusEvaluatorTests.cs`
  - `tests/SessionGuard.Tests/MainWindowViewModelWorkflowTests.cs`

## Architecture

- definitive restart state still depends on higher-confidence reboot signals
- low-confidence restart clues continue to flow through the same ambiguous-signal path used for Windows Update orchestration hints
- the change tightens interpretation without removing the underlying registry signal from diagnostics

## Limitations

- SessionGuard still surfaces pending file rename operations in technical details because they can matter in some environments
- ambiguous restart evidence can still keep the overall state cautious when active work is present
- SessionGuard still does not guarantee prevention of every Windows restart path
